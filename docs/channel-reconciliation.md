# 每日渠道对账与差异待办

## 本期范围与安全边界

沿用现有 Python/Django 项目的汇付接口和官方 Python SDK `dg-sdk==2.0.24`，
新增独立 `reconciliation` 应用，不替换订单、钱包或渠道资金流水。

- 按交易日期、商户环境范围、账单类型唯一建批次。
- 交易账单核对达人订单、活动订单、充值、退款和平台余额支付结算。
- 组合支付只比较渠道支付/退款部分，不拿订单总价比较。
- 分账账单核对请求、原交易、收款方、金额、状态及有明确口径的手续费。
- 出金账单仅做已能关联的流水检查；个人手动提现覆盖范围尚需汇付确认。
- 商户/用户结算模板没有逐笔请求号，因此生成财务核查事项，**不按同额推断银行卡到账**。
- 本地成功但当日渠道未找到、渠道有本地无、金额/状态/收款方不一致、重复流水、
  未知类型/费用不完整以及账单获取失败均保留待办。
- 页面“已核对项一致”仅表示本批已覆盖项一致；不代表全部资金、手续费或银行卡到账已核实。
- 不补款、不退款、不执行分账、不改原流水、不自动解除资金冻结。

## 官方合同与适配依据

已核对官方[文件查询文档](https://paas.huifu.com/partners/api/doc/jyjs/api_jyjs_wjcx.md)
（2026-05-07 版本）及其中交易、分账、出金、商户结算和用户结算 CSV 模板。
接口为 `POST /v2/trade/check/filequery`，通过 SDK 的 `V2TradeCheckFilequeryRequest` 调用；
查询 `file_date` 是账单生成日期，本实现查询交易日期的次日。
账单权限是否开通仍需向汇付运营确认。

技能依据：`copilot-existing-system`、`aggregation-query-reconciliation`、
`shared-server-sdk-matrix`、`aggregation-python-adapter`。不改变已有支付协议或终态规则。

签名验证后才读取下载地址；只允许明确配置的 HTTPS 官方主机，禁止重定向、内网目标，
不记录签名链接，不落原始账单文件。压缩包限制下载 20 MiB、解压 100 MiB、100 个 CSV、
20 万行；超限、格式变化或未知字段口径按失败/待核查处理，不静默跳过。
UTF-8 / GB18030 解码，金额按十进制分解析，不使用浮点数。
数据库只保存白名单差异字段及证据摘要，不保存原始卡号、账户名或完整 CSV。

## 上线配置（默认关闭）

先部署并执行数据库迁移，确保 API、worker、beat 使用相同镜像：

```sh
sudo bash ./deploy-docker.sh deploy --migrate
```

在服务端配置以下项；**不要配置在小程序前端**：

```dotenv
HUIFU_RECONCILIATION_ENABLED=true
# 改成实际希望开始核对的交易日期；自动任务最多回查最近 7 天。
HUIFU_RECONCILIATION_START_DATE=2026-10-20
# 默认官方下载主机；仅在核实汇付返回的新主机后按逗号追加，禁止通配符。
HUIFU_RECONCILIATION_DOWNLOAD_HOSTS=file.cloudpnr.com
```

还需已有汇付正式环境、商户号、系统号、产品号及正确签名/验签密钥配置。
不得为了对账打开付款或提现开关。单独打开每日对账不会触发付款。
本期新增迁移 `reconciliation/0001_initial` 和 `backoffice/0042_reconciliation_permissions`。
如果同次发布包括此前余额结算改动，也应正常执行其迁移，不手动跳过。

beat 每 30 分钟检查；北京时间 18:30 后开始拉取前日及最近 7 天账单。
当前文档提到提现账单 17:15 生成且建议一小时后下载，因此采用保守窗口。
每个日期/类型每天最多尝试 3 次、间隔至少 2 小时；完整批次当天不自动重复查询。
每批次有 30 分钟租约，过期任务不能覆盖新任务结果。
重复账单不会重复建差异；相同证据不会反复产生未读提醒，证据变化会重新打开并增加版本号。
失败重试保留上次核对结果，同时明确标记本次未完成，不能当成零交易。

历史日期或失败批次可运行只读渠道核查：

```sh
# 仅查本地结果，不请求渠道。
sudo bash ./deploy-docker.sh manage reconcile_channel_bills inspect --date 2026-10-20
# 请求该交易日期对应的渠道账单并登记差异；仍受开关、起始日期和重试限额约束。
sudo bash ./deploy-docker.sh manage reconcile_channel_bills run --date 2026-10-20
```

命令日期必须早于当天且不早于配置起始日期。需要回查更早历史账单时先明确回溯范围，
再调整起始日期并逐日核查；自动任务不会一次性请求全部历史。

## 后台操作

入口：财务管理 → 每日对账；运营总览实时待办增加“渠道对账差异待核查”。
支持日期、账单类型、流水/说明检索、分页及包含已结案记录；单条待办直达原差异。

仅全平台数据范围可授权：

- `reconciliation.view`：查看账单/差异。
- `reconciliation.manage`：开始核查、提交凭证与处理结论。
- `reconciliation.review`：另一位财务复核结案或退回。

既有 `platform-admin` 全平台角色通过迁移补充权限；其他角色手动授权，
城市角色即使误配权限也不能访问平台级账单。
处理链：待核查 → 核查中 → 待复核 → 人工核查已结案。
提交复核必须有内部凭证编号和说明；复核不能由参与核查的同一人完成。
全过程保留操作人、时间、凭证、说明和版本，过期页面不能覆盖新证据。
结案是对差异工单的处理结论，不会把业务流水强行改成成功。
重新对账确实无差异时可标为“重新对账已一致”，历史事件仍保留。

## 启用前验收

1. 汇付确认账单权限、平台/子用户覆盖范围、正式下载主机及生成日期口径。
2. 用实际小额交易核对充值、达人/活动支付、退款、延时分账和余额支付样本。
3. 确认余额支付账单的商户范围，以及分账多收款行手续费的分摊/重复口径；
   未明确前保留费用待核查，不推测相加。
4. 核对个人手动提现具体出现于哪个账单及对应银行凭证。当前不宣称已自动覆盖。
5. 测试 worker 中断恢复、独立两位财务权限、差异待办、账单缺失报警。
6. PostgreSQL 上验证并发租约与复核锁。离线 SpatiaLite 测试不能替代这一项。

本模块测试全用合成账单与 mock HTTP，不连接生产数据库或真实支付接口。
无需新增短信/微信通知；本期沿用站内实时待办和未读机制。
