# 达人订单分账准备（第一阶段）

> 本文记录第一阶段本地准备层。第二阶段新增默认关闭、仅测试白名单且命令行显式确认的延时分账试点，见 [受控分账接入](provider-distribution-pilot.md)。准备层本身仍不出款，后台 `execution_enabled=false` 仍表示后台没有执行按钮/API；真实渠道状态单独返回 `distribution`。

## 当前边界

在现有 Django/Python 聚合支付系统上增量增加本地分账准备记录。保留订单号、支付入口、订单佣金快照、退款分配规则、账务结算状态与冻结期。

**本阶段不调用汇付分账、账户支付、转账或银行卡出款接口。** 不更改下单的延时入账参数，不增加可以开启真实出款的环境变量或后台按钮。API 的 `execution_enabled` 固定为 `false`，不是待运营开启的配置项。

平台账务 `settled` 只表示内部核算完成，不表示渠道已分账，更不表示银行卡到账。运营端「交易与结算 → 达人结算」单独展示账务状态、资金来源、分账准备状态及未出款原因。

## 数据与一致性

- `ProviderOrderSettlementPlan` 与账务结算单一对一。达人、订单及佣金依据继承原结算单，不接受客户端指定收款方或分账金额。
- 金额以分保存，数据库约束为：实付 = 已退 + 达人应结算 + 平台抽成。
- 支付来源必须核对支付单、本人钱包支付分配、余额扣款状态及成功退款分项。分类为全额外部支付、余额、混合、待核实；不按支付渠道名称猜测历史资金构成。
- 无法核对的来源金额返回 `null`，不是零。`locally_reconciled` 只表示本地记录一致，`channel_funds_verified` 始终为 `false`。
- 原支付请求日期、请求流水号及渠道支付流水号保存在来源快照中。它们不是分账请求流水，不得复用为新的资金操作流水。
- 按「订单 → 结算单 → 准备单」顺序加行锁。同一订单重复执行不新增准备单；只有快照变化才增加一条 `ProviderOrderSettlementPlanRevision`。原快照不覆盖。
- 准备单、快照审计与关联业务变更在同一事务中，审计写入失败时共同回滚。

## 手续费规则（平台承担）

2026-10-03，业务方确认已开通延时交易及向个人用户分账的能力，并指定手续费由平台承担。权限记录来自业务方确认，不是本次查询汇付配置或真实资金验收的结果。

- 按现有订单佣金快照，先计算达人应结算与平台抽成，再将手续费计入平台费用；不先从服务费扣手续费后再按比例分成。
- 70% / 30% 是业务方举例，不是全局改价：不修改后台分类配置，不重写历史订单的佣金快照。仍仅对退款、优惠后的净服务费计佣，交通费及其他费用仍按现有规则归达人。
- 以参与分成的服务费 100 元、平台抽成 30% 为例，达人应得 70 元、平台扣费前 30 元；**假设**核实的手续费合计 0.60 元，平台扣费后净额为 29.40 元，达人仍为 70 元。0.60 元不是本系统配置费率。
- 本地规则覆盖支付、分账及银行卡结算手续费。三类费用须分别核对实际扣费方与金额，不能把一种费用的配置当成全部费用配置。银行卡结算可能按批次计费，不得给每笔订单重复记整批费用。
- `fee_policy_snapshot` 保存本地政策、达人不扣手续费的应收金额和平台扣费前抽成，并写入版本审计。历史空快照显示待核实；正常业务刷新才记录当前准备规则，不代表授权补付历史订单。
- 实际手续费未接入核账，本阶段三类费用均为 `null`；未知不能当作零，平台扣费后净额也为 `null`。金额计算函数只接收以分为单位、已经核对的费用；没有费用证据的接口不允许前端填数确认手续费。
- 费用超过平台抽成时保留负净额与平台资金缺口，不能扣减达人应得收入或把亏损截成零。未来执行时须有平台资金补足并核实渠道可用余额；不能因设置了平台承担就假定资金充足。
- 部分退款继续按原订单佣金快照重算达人、平台份额；不假定手续费同比例退回。全额退款也不证明原支付手续费已退。

`orders/settlement_fees.py` 仅做本地整数金额核算，不生成渠道请求。当前准备单不再无条件添加 `channel_fee_policy_unverified`、`external_route_unconfirmed`、`execution_disabled`：渠道资金、费用、收款人及执行开关由分账执行器独立核验，实际结果保存于分账/提现单。`execution_enabled=false` 仅表示后台页面没有资金执行按钮/API，不表示后台任务开关关闭。

官方核对：交易确认用于分配已有延时交易的资金；其请求分账明细不能凭空增加费用承担字段，响应中的费用与承担方也不能反向复制成请求。商户业务配置另有交易手续费与分账配置域，接入时必须按各自完整合同、真实平台账户和官方 SDK 处理。[交易确认](https://paas.huifu.com/partners/api/doc/smzf/api_jyqr.md)、[商户业务开通修改](https://paas.huifu.com/partners/api/doc/shgl/shywkt/api_shjj_shywktxg_kyc.md)。本次未发送商户配置修改、分账或银行卡出款请求；实际手续费、扣费账户及退款返费规则仍需渠道证据核验。

## 更新时机及状态

确认完成生成账务结算、推进冻结期、用户/后台登记及审核售后、生成退款、退款成功时同步准备记录。没有结算单时不创建准备记录。

- `waiting`：尚未满足账务条件，例如未确认完成、冻结期未到、售后未完、退款未完或账务未结算。
- `ready`：本地业务条件已满足；不代表试点授权、渠道资金核验、已执行分账或银行卡到账。
- `blocked`：账务条件已满足，但资金链路未接通或仍需核实。此状态不能发起付款。
- `cancelled`：账务结算已取消或已经全额退款，无需执行分账。

后台展示的是 `evaluated_at` 时点的准备快照，读取列表不改账、不刷新准备记录，不产生历史补付。未来真正发起出款前必须再次核对实时状态，不能把这份缓存快照当付款授权。

补齐的账务防护：即使没有售后单，只要存在待退款、处理中或失败待处理的退款，结算推进仍保持争议冻结；失败不等于退款责任已经消失。

## 历史数据与部署

迁移 `orders/0027_provider_settlement_plan.py` 只创建两张表及约束，`0028_provider_settlement_fee_policy.py` 增加默认空对象的费用规则快照，**不扫描、回填或支付历史订单**。正常发布时须先完成迁移，再启动包含本功能的 API/任务进程。

`0030_provider_settlement_plan_ready.py` 增加业务就绪状态，不批量改写既有审计版本。既有准备单在下次正常业务同步/执行预检时重新评估；后台只读页面仍显示最近核对时间。准备状态与渠道执行结果分栏展示，不以准备单的未知费用遮盖已核验的分账费用。

既有结算单没有准备记录时返回 `distribution_plan: null`，运营端明确显示需核账。后续业务事件同步到这类记录时，标记 `requires_manual_review=true`，普通刷新不能消除该标记。本阶段无人工解除或执行资金操作的接口。

仍需与汇付及平台运营确认后才能继续：

1. 在业务方已确认开通能力的基础上，核验商户/个人接收账户实际生效状态、分账上限，以及三类费用的实际扣款账户与费率。平台承担是业务规则，不替代渠道验证。
2. 钱包余额资金的实际归集位置、可用资金及适用的账户支付/划转产品；不能把平台钱包扣款当汇付余额支付。
3. 退款前后资金回退方案、混合支付两部分的对账与补偿。
4. 历史订单的真实渠道状态、已退款及既有出款记录；另行设计受控补结算。

未来资金适配层须使用官方 SDK，保持验签、订单/金额/主体核对、请求幂等及查询补偿；是否处理异步通知以具体接口合同为准。同步受理和本地任务成功均不能冒充渠道终态。私钥仍仅从服务端安全配置读取。
