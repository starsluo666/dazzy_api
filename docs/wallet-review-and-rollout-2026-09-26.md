# 余额充值与本批改动交付检查

## 提交范围

本批包含余额/充值、达人及活动订单余额支付、营销优惠券/邀请礼包、后台菜单、用户端反馈/账号安全等已累积修改。根仓库既有文档与设计稿删除、临时目录不在本次业务提交范围。

## 本轮修复

- 组合支付取消后的迟到成功：释放原冻结余额，仅对外部实收差额发起退款；支付与退款任务在同一事务落库。
- 历史全外部支付：已发起的汇付流水不因用户后来充值而重算；历史支付金额展示不使用当前可用余额。
- 纯余额支付：冻结、扣款与业务状态更新保持原子性，异常时全部回滚。
- 钱包初次创建支持并发；退款按原分配限额校验，独立回执覆盖纯外部退款的重复处理。
- 充值页面恢复服务端订单快照；改张数不复用旧订单；支付期间禁止改张数；配置改变需重新确认价格。
- 后台充值参数使用类型、范围与长度校验，配置修改保留审计日志。
- 钱包及拉新全局数据限定平台权限范围，城市角色不能越权；财务只读角色不自动获得充值配置写权限；平台管理员授予命令补齐钱包权限。
- 注销账号检查未结余额、冻结余额及待核对充值，并与创建充值单串行处理。
- 定时充值查单补偿缺失通知；未发起网关请求的过期单本地关闭，已发起单不因本地倒计时而假定支付失败。
- 营销模板被活动规则引用时禁止直接删除；邀请汇总统计不再被最近 100 条展示限制截断。

## 资金规则与边界

金额均为整数分。每张面值固定 1000 元，充值实付按后台张数档位计算，余额按面值入账。下单优先使用余额，余额足够时不走组合支付，不足时外部支付仅收差额。退款按原支付构成退回，充值余额不提供提现入口。

这是既有 Django/Python 汇付 V4 聚合支付系统的增量修改，不替换官方 SDK、验签或退款接口。前端回跳不是支付成功依据；充值入账由服务端核对商户、流水、金额、交易类型与终态后幂等完成。没有使用生产真实扣款验证资金到账。

本轮使用 `huifu-pay-integration` 的存量系统、异步通知、聚合退款三份 reference，重点核对事务边界、资金终态、幂等及退款上限；不新增或猜测渠道协议。

- Django 系统检查、migration 一致性检查、相关 Python 静态检查与暂存差异空白检查通过。

## 部署顺序

1. 备份业务数据库，随本批代码部署全部 migration（含 wallets、growth、优惠券及权限迁移）。
2. 重启 API、Celery worker 和 beat。新增 `wallets.reconcile_pending_recharges` 每 60 秒运行，部署后检查任务被 worker 注册。
3. 后台确认“财务管理 → 余额与充值”的可见与配置权限；充值默认关闭，运营配置折扣后再开放。
   如果测试环境曾提前执行过本批未提交的权限迁移，需另行核对既有角色：只读财务/营销角色不应持有 `wallet.manage` / `growth.manage`，不能依靠重新运行已应用的迁移纠正历史授权。
4. 发布后台与用户端，清理旧静态资源缓存。当前充值前端仅开放微信服务号 H5，小程序与原生 App 不宣称已开放真实充值。
5. 用已批准的真实商户环境验证：充值成功/取消/通知丢失、余额全额支付、组合支付、取消后迟到到账、部分/全额退款及原渠道到账。持续非终态或查单异常的充值须人工核对，不能直接改为成功。

本次代码检查与提交不执行业务数据库迁移，不进行推送或生产部署。
