# 余额充值与本批改动交付检查

## 2026-10-09：消费折扣改造（以下旧交付记录保留供追溯）

- 新充值单采用 `wallet-consumption-v2`：实付 = 入账面值，消费折扣随充值批次保存；配置调整不修改既有批次。
- 达人订单采用 `provider-order-pricing-v2`：先用优惠券抵服务费（不抵交通费），剩余服务费按可用批次的最优折扣整单计价，最后加全额交通费。券使用门槛沿用原订单总额口径。
- 例：100 元服务、95 折余额剩 50 元，其他余额为 0，应付 95 元，余额 50 + 微信 45；若另有 97 折余额，则先扣 95 折 50 元，再扣 97 折 45 元，不需要微信。即使最优批次仅余 1 分，本单仍整单享受该折扣。
- 扣款按折扣从优到次、同折扣按批次先后进行，最后使用普通/历史余额；总余额不足才外部补差。活动订单仍按原价消费余额，不享受达人折扣。
- 折扣订单创建时冻结支付余额与批次；服务器对预览价格签名并在持有钱包锁时重算，5 分钟内有效，金额/折扣变化需重新确认。已创建订单锁定原金额，之后充值不重算该订单。
- 钱包写操作统一先锁所属用户、再锁钱包，避免支付完成补锁用户时与另一个新建订单产生锁顺序反转；新增查询顺序和 PostgreSQL 行锁回归项。
- 未支付取消/超时通过原支付补偿链路释放批次；已消费的退款按原余额/渠道构成退回，余额部分按原扣款顺序恢复到原批次，单批恢复不超过原扣款。使用原退款回执保证重复回调不重复恢复。
- 平台/达人分成继续基于优惠后的净服务费，路费保持原归属。此改造不开放余额/混合支付的汇付自动分账：现有渠道分账准入限制保留，不能把本地分成计算等同于已完成渠道分账。
- 历史充值单（含待支付单）保持原金额，不补发消费折扣；历史已创建订单不重新计价。迁移仅建批次表、扣款明细表，不重写资金数据。

部署前需执行 `wallets.0005_wallet_balance_lots` 并同时更新 API / worker / beat、用户端、后台。
新旧后端不能混跑；旧代码不知道批次，消费后将造成汇总与批次不一致。已有新批次后不要直接回滚旧代码或删除迁移表，应先暂停充值与余额消费，核账后另行制定回退方案。
旧客户端无报价确认凭据时不能创建折扣订单，需更新客户端；历史待支付充值单仍可继续按原快照支付。

本次使用 `huifu-pay-integration`：`copilot-existing-system.md`、`copilot-solution-selection.md`、`shared-async-notify.md`。
存量 Python/Django 汇付 V4 聚合支付的 SDK、流水号、验签、通知和查单确认均保留，不发起真实渠道请求。
测试入口：`scripts/check_wechat_auth.py wallets.test_consumption_discount`；PostgreSQL 并发项由 `scripts/check_postgres_regression.py wallets.test_consumption_discount` 在隔离临时库执行，不能以 SQLite 跳过代替通过。

## 本轮修复

- 组合支付取消后的迟到成功：释放原冻结余额，仅对外部实收差额发起退款；支付与退款任务在同一事务落库。
- 历史全外部支付：已发起的汇付流水不因用户后来充值而重算；历史支付金额展示不使用当前可用余额。
- 纯余额支付：冻结、扣款与业务状态更新保持原子性，异常时全部回滚。
- 钱包初次创建支持并发；退款按原分配限额校验，独立回执覆盖纯外部退款的重复处理。
- 充值页面恢复服务端订单快照；改张数不复用旧订单；支付期间禁止改张数；配置改变需重新确认价格。
- 后台充值参数使用类型、范围与长度校验，配置修改保留审计日志。
- 钱包及拉新全局数据限定平台权限范围，城市角色不能越权；财务只读角色不自动获得充值配置写权限；平台管理员授予命令补齐钱包权限。
- 注销账号检查未结余额、冻结余额及待核对充值，并与创建充值单串行处理。
- 定时充值查单补偿缺失通知；未发起网关请求的过期单本地关闭，已发起单不因本地倒计时而假定支付失败。
- 营销模板被活动规则引用时禁止直接删除；邀请汇总统计不再被最近 100 条展示限制截断。

## 资金规则与边界

此段为 2026-09-26 的历史口径，已由上述 2026-10-09 消费折扣规则替代。金额均为整数分，每张面值固定 1000 元。旧版本在充值时按档位优惠并按面值入账，新版本不再采用这一方式。退款按原支付构成退回，充值余额不提供提现入口。

这是既有 Django/Python 汇付 V4 聚合支付系统的增量修改，不替换官方 SDK、验签或退款接口。前端回跳不是支付成功依据；充值入账由服务端核对商户、流水、金额、交易类型与终态后幂等完成。没有使用生产真实扣款验证资金到账。

本轮使用 `huifu-pay-integration` 的存量系统、异步通知、聚合退款三份 reference，重点核对事务边界、资金终态、幂等及退款上限；不新增或猜测渠道协议。

## 部署顺序

1. 备份业务数据库，随本批代码部署全部 migration（含 wallets、growth、优惠券及权限迁移）。
2. 重启 API、Celery worker 和 beat。新增 `wallets.reconcile_pending_recharges` 每 60 秒运行，部署后检查任务被 worker 注册。
3. 后台确认“财务管理 → 余额与充值”的可见与配置权限；充值默认关闭，运营配置折扣后再开放。
   如果测试环境曾提前执行过本批未提交的权限迁移，需另行核对既有角色：只读财务/营销角色不应持有 `wallet.manage` / `growth.manage`，不能依靠重新运行已应用的迁移纠正历史授权。
4. 发布后台与用户端，清理旧静态资源缓存。当前充值前端仅开放微信服务号 H5，小程序与原生 App 不宣称已开放真实充值。
5. 用已批准的真实商户环境验证：充值成功/取消/通知丢失、余额全额支付、组合支付、取消后迟到到账、部分/全额退款及原渠道到账。持续非终态或查单异常的充值须人工核对，不能直接改为成功。

本次代码检查与提交不执行业务数据库迁移，不进行推送或生产部署。
